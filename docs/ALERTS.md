# Slack Alerts

The collector pushes cluster alerts through the Slack Web API. Configuration
is hot-reloaded. Root searches `/etc/sgpu/slack.json` before home
`~/.sgpu/slack.json` / `webhook.json`; other users search home before `/etc`.
`SLURM_GPU_TUI_SLACK_CONFIG` explicitly selects a file. Token and channel are
required; a legacy incoming-webhook URL alone does not enable notifications.
`sgpu doctor` reports the selected path and enabled state.

Alerts are generated by the collector from the merged Slurm/GPU snapshot, not
by the TUI. They continue even when no terminal UI is open.

## Setup

Create a Slack app with the `chat:write` scope, install it, invite it to the
channel (`/invite @your-bot`), and configure its token and channel. Alerts post
as replies under **one parent message per
day** (`📅 GPU cluster alerts — date`), keeping the channel tidy. The collector
creates that parent at the start of each day even when there are no alerts, so
a healthy day remains visible with zero replies. The native installer does
not prompt for or print tokens. Set `SGPU_SLACK_BOT_TOKEN`,
`SGPU_SLACK_CHANNEL`, and optionally `SGPU_SLACK_SENDER` / `SGPU_SLACK_LANG`,
then run `sgpu-install slack-config` (optionally `--output PATH`). Export secrets
using the site's secret mechanism, keeping them out of shell history. A master
install also writes config when `SGPU_SLACK_BOT_TOKEN` is set. Existing extra
keys are preserved, malformed existing config is rejected, and output mode is
0600. Runtime token fallback is `SLURM_GPU_TUI_SLACK_BOT_TOKEN`; service units
never embed the token.

## Quick check

```bash
sgpu doctor
```

Expected Slack line:

- `slack: bot daily thread (selected config path)`

If it says `not configured`, check the selected path, mode and service user.
The file must be regular, owned by root or the service UID, and not writable
by other users. Keep mode 0600 for credentials.

## Config keys (`~/.sgpu/slack.json`)

| Key | Default | Meaning |
|-----|---------|---------|
| `bot_token` / `channel` | — | Required bot credentials; alerts use daily-thread grouping |
| `sender_name` | `AI-master` | Identity shown in every alert (set per cluster to tell them apart) |
| `lang` | `en` | Alert language: `en` or `ko` |
| `node_health` | `true` | Node down/recovered, judged by validated Slurm state |
| `down_grace_sec` | `180` | Down must persist this long before alerting (rides out cold starts / blips) |
| `collect_alert` | `true` | A GPU node that was reporting goes blind (dead agent / hung node) while SLURM still shows it up |
| `collect_grace_sec` | `600` | Publication loss must persist this long; recovery runs locally on the node |
| `waste_alert_hours` | `0` | GPU idle/parked ≥ N hours (`0` = off); config writer seeds `2` |
| `rogue_alert` | `false` | GPU used outside SLURM; config writer seeds `true` |
| `rogue_grace_sec` | `300` | Rogue use must persist this long before alerting (rides out job start/end races) |
| `temp_alert_c` | `0` | GPU temperature ≥ N °C (`0` = off; ~90 typical) |
| `ecc_alert` | `true` | Uncorrectable ECC errors — silent hardware failure; alert carries physical slot / /dev/nvidiaN / UUID / PCI bus / serial for RMA |
| `job_done_users` | `[]` | Notify when these users' jobs finish |
| `job_fail_users` | `[]` | FAILED / OOM / TIMEOUT / NODE_FAIL alerts for these users; `["*"]` = everyone (needs sacct) |
| `pending_alert_hours` | `0` | Job stuck `PENDING` on the scheduler ≥ N hours (`0` = off; user holds / dependencies never alert) |
| `dm_users` | `{}` | `{"login": "U012AB..."}` Slack member ids — alerts about a user's own jobs are also DMed to them |
| `free_gpus_min` | `0` | Notify when free-GPU count reaches N (`0` = off) |
| `mem_fair_factor` | `0` | RAM-hog alerts: a job's **requested** RAM exceeds factor × its GPU fair share (node RAM × job GPUs ÷ node GPUs). `1.0` = strict, `0` = off. Allocation-based — catches greedy `--mem` before the memory is even touched; silent on clusters where jobs don't request memory |

Repeated conditions are debounced (30 min for events, 6 h for standing
conditions like waste/temp/ECC). Node-health alerts follow validated Slurm
state for all nodes. Collection-loss alerts apply to GPU publishers. Scheduler
failure does not infer node outages or finished jobs.

## Alert semantics

- **Node down/recovered:** based on Slurm node state (`down`, `drain`, `fail`,
  `err`, `boot`) after `down_grace_sec`.
- **Collection lost/restored:** a GPU node was previously reporting, Slurm still
  says it is up, but sgpu can no longer collect GPU data after
  `collect_grace_sec`.
- **Wasted GPU:** a GPU is allocated but has no compute process, or VRAM is held
  with near-zero utilization, for at least `waste_alert_hours`.
- **Rogue GPU:** a GPU has a process but no Slurm GPU allocation, persisting
  for `rogue_grace_sec`. Jobs in `COMPLETING` state still count as allocated
  (process teardown can outlive `RUNNING`), and rogue checks are skipped on
  cycles where the Slurm controller query failed or a node's data is stale —
  both would otherwise flag legitimate users.
- **Temp/ECC:** temperature over `temp_alert_c`, or uncorrectable ECC errors.
  ECC alerts include hardware identity fields when the driver exposes them.
- **Free GPUs:** fires when the free-GPU count crosses from below to at least
  `free_gpus_min`.
- **Job done:** tracks currently visible jobs for `job_done_users`; when a job
  disappears from the running queue, a completion alert is sent.
- **Job failed:** when a tracked job (for `job_fail_users`) leaves the queue,
  slurmdbd is asked for its outcome; `FAILED`, `OUT_OF_MEMORY`, `TIMEOUT` and
  `NODE_FAIL` raise an alert. Clean finishes stay silent unless the user is
  also in `job_done_users`. The owner's DM (never the shared channel —
  stderr can leak paths/secrets) carries the last ~15 lines of the job's
  stderr when the file is readable.
- **RAM over fair share** (`mem_fair_factor`): a running GPU job requests
  more memory than factor × its share; posted to the channel and DMed to
  the owner, re-alerted every 6 h while it persists.
- **Pending stuck:** a job waiting on the *scheduler* (`Resources`,
  `Priority`, …) for `pending_alert_hours`. Holds, dependencies and
  begin-times are the user's own doing and never alert.
- **Personal DMs:** with `dm_users` set, job done/failed and
  pending-stuck alerts about a user's jobs are also sent to them directly.

## Minimal bot config

```json
{
  "bot_token": "xoxb-...",
  "channel": "#gpu-cluster",
  "sender_name": "AI-master",
  "lang": "ko",
  "node_health": true,
  "collect_alert": true,
  "waste_alert_hours": 2,
  "rogue_alert": true,
  "ecc_alert": true,
  "temp_alert_c": 0
}
```

Keep this file mode `600`; it contains Slack credentials. Do not paste tokens
into issue reports or shared logs.

Delivery and outcome work use bounded queues (200 messages, 8 outcome batches
of at most 32 jobs). HTTP requests time out after 10s and retry at most three
times; rate-limit waits are capped at 60s. Failed event delivery releases its
debounce reservation so a continuing condition can retry. Daily-parent failure
has a 60s cooldown. This is not a durable outbox or a guarantee of delivery.

The TUI shows the same job/node transitions as toasts while it's open, so you
don't need Slack for at-the-terminal awareness.
